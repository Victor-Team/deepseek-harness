# Agent Note：omp subagent 后端

Status: implemented

[English](2026-09-03-omp-subagent-backend.md) | 中文

## 问题

想让委派的子代理跑在父级 provider 路由所不提供的模型上，目前有两个进程外选项，而两者都把模型选择限制在 harness 自身能触达的范围内：ACP 后端需要一个讲 ACP 的子代理，Claude Code 与 Codex 后端各自绑定一个产品。没有任何一个能让组合委派给第三方 CLI 持有的任意模型目录。

[omp](https://github.com/can1357/oh-my-pi) 从一个安装里解析跨多家提供方的模型，包括 harness 并不持有凭据的订阅制路由。要触达它，需要一个讲它协议的后端。

## 决定

新增 `dsh-subagent-omp`：一个一次性进程外提供方，spawn `omp --mode rpc --no-session` 并通过 omp 的换行分隔 RPC 协议驱动子代理。它与 ACP、Claude Code、Codex 后端并列接入 seam，共享它们的约定——每次运行一个全新进程、以父会话 cwd 为工作区、只有子代理的最终答案回传。

### 刻意只用协议版本 1

omp 在 `ready` 帧中声明 `supportedProtocolVersions: [1, 2]` 并默认为 1。版本 2 为超出传输上限的帧引入 `rpc_chunk` 分片。一次发送单个 prompt、读取单个最终答案的运行不需要重组，因此客户端讲 v1，并把分片帧当作协议故障。静默重组意味着为一个本提供方并不服务的场景背负半帧状态；明确失败则意味着未来默认值一旦变更，会表现为报错而不是被截断的答案。

### `agent_end` 不是结算信号

当某个 `agent_end` 所属会话已经排定了自动续跑——自动重试、空停止重试——omp 会在其上设置 `willContinue: true`，而它自己的协议类型写明订阅方不得把它当作用户可见的终态结算。因此客户端会等待不带该标志的 `agent_end`。

这是整个协议中唯一一处「看似合理的读法会产出静默正确性缺陷」的地方：把第一个 `agent_end` 当作终态，会返回 omp 决定重试那一刻已有的文本——它看起来像一个完整答案，其实不是。

### 最终答案取自 `get_last_assistant_text`

终态轮次之后，客户端发一条 `get_last_assistant_text` 命令，而不是折叠流式的 `text_delta` 与 `message` 帧。omp 已经算好了这一选择，折叠流会重新实现它的答案选择规则并与之漂移。因此客户端只对四类帧作出反应，忽略其余所有事件。

## 备选方案

**把 omp 注册成 `ctx.llm` 上的 LLM adapter，而不是 subagent 提供方。** 这条路最先被调查，因为它能让 omp 的模型在 harness 路由模型的任何地方都可选。它走不通：omp 的 `prompt` 命令只携带单个 `message` 字符串，没有结构化消息数组；而 omp 经 `set_host_tools` 接受的宿主工具会被包装成 omp **自己的** agent 工具——omp 在其上跑自己的循环，并在每个结果之后继续，直到 `agent_end`。因此一次 `prompt` 是一整个 agent 轮次，而不是一次模型请求，`llm.stream()` 无法在不溶解 harness 自身 step 边界的前提下被它满足。

**折叠流式帧，而不是索取最终文本。** 流中携带 `message`、`text_delta` 与 `output_text` 帧，答案是可以累积出来的。已否决：omp 自己的答案选择是权威的，而且已经作为一条命令暴露；在此重新实现它，会产生第二套选择规则——每当 omp 改动自己的规则，这套规则就会与之静默不一致。

**讲协议 v2 并重组分片。** 以「对本提供方属投机」为由否决——理由见上面的决定。当某个消费方确实需要超出上限的帧时它才成立，而一次性最终答案并不需要。

**复用 Codex 后端的 JSON-RPC 传输层。** 已否决，因为 omp 的协议不是 JSON-RPC：它在扁平的命令帧与响应帧上用 `id` 字段关联，并在其间穿插不关联的事件帧。共享传输层对这两点都没有建模，复用意味着把它掰向第二种协议，而不是共享一种协议。

## 后果

组合现在可以委派给被 spawn 的那个 omp 安装所能解析的任意模型，而 harness 既不持有那些凭据、也不知道那份目录。代价是可触达的模型变成了一个 harness 并不管理的安装的属性：期望使用订阅制路由模型的部署必须自行确保该安装已认证，而指向某个 profile 作用域包装脚本的 `command` 会静默地把目录收窄到该 profile 的提供方。README 对两点都作了陈述。

本提供方不声明任何可选能力。omp 的 `--append-system-prompt` 本可承载角色设定，但它接受的是文件路径而非内联文本，因此支持它意味着为每次运行写一个临时文件——选择延期，而不是做一半。

客户端只对四类帧作出反应、忽略其余，这对一次性答案是充分的，对任何需要观察子代理工作过程的用途则是不充分的。流式投影、宿主工具透传与可续子代理各自都需要拓宽客户端，而每一项都应当与消费那些帧的 seam 工作放在一起。

## 测试

覆盖客户端的帧处理与终态轮次规则，以及运行生命周期的校验与 argv 构造。真正要紧的是协议层断言：带 `willContinue: true` 的 `agent_end` 不得结算一次 prompt、分片帧必须使线路失败而不是被重组、`success` 不为真的响应帧必须拒绝其关联的等待者。一个驱动该线路的 mock 子进程可以在不 spawn omp 的前提下覆盖这些。

不做无密钥 snapshot：真实运行会触达一个第三方 CLI，其模型目录与认证属于宿主状态，而无密钥流水线刻意不依赖这类状态。
