# Agent Note：为 Claude Code 与 Codex 子代理提供方加入 `persona`

Status: implemented

[English](2026-09-03-cli-subagent-persona.md) | 中文

## 问题

这两个订阅制 CLI 子代理提供方声明的是 `NO_START_CAPABILITIES`，因此共享接缝会在提供方看到请求之前就拒绝每一个 `persona` 请求。在把多个委派工具组合成一份名册的部署里，这让 CLI 成员在结构上不同于进程内成员：进程内子代理会以受作用域限制的 `deployment:persona` 段接收角色设定，而 CLI 子代理什么也收不到，调用方只能把角色手写进每一段任务文本，再给每条回答加注「未按格式」。这是一份本该由提供方承担、却落到每次调用上的编写负担。

两个产品都能承载按子代理指定的角色；两个提供方都没有传。

## 决定

在两个提供方上声明 `persona: true`，并把请求文本交给各自产品的机制处理。两者的机制差异足够大，能力标志是它们唯一的共同点。

### Claude Code —— 追加到原生 preset

Agent SDK 的 `systemPrompt` 接受 `{ type: 'preset', preset: 'claude_code', append }`。提供方采用这一形式，因此角色设定叠加在 Claude Code 原生系统提示之上，而不是替换它。这维持了本包既有的立场：原生设置与产品配置保持权威——提供方刻意省略 `settingSources`，而一个替换掉 preset 的角色设定会静默地推翻这一点。没有角色设定时该选项保持未设置，而不是传一个空的 append，因此不带角色设定的运行与改动前逐字节一致。

### Codex —— 首个文本块，而非系统指令

app-server 协议没有自定义系统提示字段。`thread/start` 接受 `personality`（预定义枚举，不是自由文本），`turn/start` 仅在 collaboration 模式下接受 `settings.developer_instructions`；两者都无法承载任意角色。因此角色设定成为该轮次的首个文本块。

这是比 Claude Code 更弱的保证，文档中已如实标注：模型可能把角色设定当作任务内容，而不是当作优先于任务的指令。它在 `textTask` 内部、校验**之后**才追加，因此角色设定无法让一个本来为空的任务变得合法——空值检查仍然只针对调用方给出的块。

这种不对称是有意为之，而非漏掉的抽象。一个共享的「给角色设定加前缀」辅助函数会掩盖如下事实：一个提供方拿到的是系统指令，另一个拿到的是任务文本。而这恰恰是调用方在斟酌角色措辞力度时需要知道的事实。

## 备选方案

**不声明该能力，继续把角色写进任务文本。** 这是改动前调用方的做法，而且它是有效的——模型确实会读提示里陈述的角色。它输在两点：角色要按每次调用重新编写，而不是按每个委派工具声明一次，因此一份有多个 CLI 成员的名册要到处重复；而且对 Claude Code 来说，它放弃了 SDK 本就提供的真正系统提示槽位，让角色与任务处于同一位阶，而产品本可以让它高于任务。

**替换 Claude Code 的 preset，而不是追加。** `systemPrompt` 也接受纯字符串，这会让角色设定完全掌控系统提示，并让两个提供方行为一致。已否决：本包的全部立场就是原生 Claude Code 设置、`CLAUDE.md` 和产品配置保持权威——提供方省略 `settingSources` 正是为了让宿主自己的设置生效。一个替换式的角色设定会静默丢弃这一切，而请求角色的调用方无从知道自己换来的是这个。

**为 Codex 的角色设定加一层人造指令外壳**（`"System: …"`，或用围栏包一个角色块）。以「虚假精确」为由否决：它把一个任务文本块打扮成系统指令，却没有改变模型实际收到的内容，这只会让更弱的保证更难被看见，而不是变强。README 选择如实陈述其位阶。

**在两个提供方之间抽取共享的角色设定应用辅助函数。** 已否决：两套机制在对调用方最重要的那个性质上并不相同——角色设定是否高于任务。共享辅助函数恰好会掩盖这一点。此处的对称性是能力标志，而它已经是共享的。

## 后果

部署现在可以像给进程内成员那样为 CLI 子代理声明角色，两个提供方接受同一个请求字段，因此名册成员在接缝处变得一致——尽管它们的保证并不相同。这份差异就是代价：`persona` 只是一个布尔值，但它对一个提供方意味着「一条系统指令」，对另一个意味着「任务里的第一段话」。两份 README 和本文都承载了这一区分，需要更强保证的调用方必须去读它们，而不能只信这个标志。

不提供角色设定的运行保持不变——Claude Code 让 `systemPrompt` 保持未设置，而不是传一个空的 append；Codex 原样返回调用方的块——因此本次改动不可能改变既有委派行为。

`turn/start.outputSchema` 存在于 Codex 协议中，目前仍未接线；Claude Agent SDK 的结构化输出路径尚未调研。强制结构化最终结果还需要结果校验与失败分类映射，那是一次独立的改动，有其自身的诊断面。两份 README 都记录了这一缺口，因此调用方从这两个提供方拿到的仍是自由格式文本。

## 测试

覆盖两处发生变化的接缝。Claude Code 侧断言 `claudeQueryOptions` 在有角色设定时产出确切的 preset-append 对象，在没有时完全不带 `systemPrompt` 属性。Codex 侧断言 `textTask` 会把角色设定放在最前、没有角色设定时序列保持不变、并且在提供了角色设定时仍然拒绝空白任务。两个提供方的注册测试与 loader 组合测试现在都断言所声明的能力集合中 `persona: true`——标志与透传必须一起改动，因为标志缺失时接缝会在提供方运行之前就拒绝请求。

不涉及 snapshot 或 e2e 改动：不提供角色设定的调用其委派转录保持不变，而提供角色设定的调用会触达真实订阅制 CLI，无密钥流水线不会运行它。
